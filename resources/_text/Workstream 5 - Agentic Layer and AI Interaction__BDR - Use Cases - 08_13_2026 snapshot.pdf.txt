BioData Registry Use Cases
Note: This is a snapshot of the first iterations beyond Jess’ original primer. It is intended to
spark conversation with other workstreams and be subject to revisions. The latter will be
informed by infrastructure and schema decisions. This is not yet a prescribed approach or
locked in design. Please leave comments to get the conversation started.

SCI — Scientist / Researcher
Consumes the Registry to find, evaluate, and access data for analysis and model training. Rarely
writes metadata; cares most about discovery, fitness, provenance, and getting to the bytes.

P0
SCI-1: Structured, faceted search. A scientist narrows results deterministically, refining
facets until the candidate set is right. Key facets to be defined based on central schema &
accelerator needs.

Success criteria:

     •   Relevance: 80% of searches return a useful dataset.
     •   Usability: scientists can combine facets to narrow results unaided—no technical
         knowledge required.
     •   Effectiveness: 80% of scientists find their intended dataset via faceted search, in
         under 2 minutes.
     •   API parity: 100% of UI facet, filter, and sort are available through the Query API and
         MCP with identical semantics—stable IDs, total counts, and deterministic
         pagination.



SCI-4: Evaluate dataset fitness before use. Before committing to a dataset, the scientist
judges whether it suits their analysis.

Key factors: 1) artifact types (raw data, analysis artifact, publication artifact), 2) metadata
completeness (FAIR score), 3) quality-control metrics, 4) lineage

Success criteria:

     •   Artifacts: scientists can review a dataset's artifact types (raw, analysis, publication).
   •   Metadata: datasets show a metadata-completeness/FAIR score with enough detail
       to interpret it.
   •   Quality: relevant QC metrics and results are visible and clearly explained.
   •   Lineage: dataset shows sources, transformations, processing steps, and related
       outputs.
   •   Decision support: scientists can compare these factors to judge suitability, with
       >80% reporting they have enough information to confidently decide on a dataset.
   •   API access: artifact type, FAIR score, QC results, and lineage summary are
       retrievable per entity via the API (not UI-only), enabling programmatic ranking and
       filtering.

SCI-5: Locate & access underlying files. Scientists retrieve the storage location(s) from
results and pull the data with native tooling (boto3, gcloud, rclone). The registry points to
the data.

Key enables: 1) File manifest download for bulk (.csv), 2) Easy copy & paste of file paths. 3)
Location prominent in UI e.g. default field?

Stretch: 1) The registry brokers credentials to further streamline user path from locate >>>
access, 2) Open [DataAsset] in CodeOcean (or other analysis platforms - neural dynamics
has some prior art in their data catalog linked w/ CodeOcean)

Success criteria:

   •   Paths: scientists can view prominent storage locations and copy paths for native
       tools (boto3, gcloud, rclone).
   •   Bulk access: scientists can download a CSV manifest of file paths and relevant
       metadata.
   •   Resolution: registry links resolve to correct file locations without duplicating or
       moving data.
   •   Permissions: access respects existing permissions and clearly flags unavailable
       locations or required credentials.

CUR — Data Curator
Registers, validates, corrects, versions, and publishes metadata. The primary writer into the
Registry and the main beneficiary of AI assistance.

P0
CUR-0 (Pre-ingest) metadata validation Curators validate data against the BioData
Registry schema and receive a validation report. This can occur: 1) standalone pre-ingest 2)
as part of the ingest flow
   •   Ingest (to production) is flagged for data with fundamental validation errors, e.g.
       controlled vocabulary flaws, missing required fields, etc.
   •   If controlled vocabulary isn’t available yet, points of contact & process to add
       support for new entries are explicitly called out.
   •   If there are issues with optional fields, ingest can proceed, but they are encouraged
       to resolve these issues to improve data discoverability. They need to explicitly
       acknowledge this dialogue.
   •   If pre-ingest validation succeeds outright, they receive a success message and are
       asked whether they want to execute the ingest now.

Success criteria:

   •   Validation: curators can validate data against the current BioData Registry schema,
       standalone or during ingest, and 80% indicate that they receive a clear, actionable
       report.
   •   Blocking errors: production ingest is flagged for fundamental errors—missing
       required fields, invalid formats, or unsupported controlled-vocabulary values.
   •   Vocabulary requests: when a required term is unavailable, the report identifies the
       process and point of contact for requesting its addition.
   •   Warnings: optional-field issues don't block ingest, but curators must explicitly
       acknowledge them before proceeding.
   •   Success: on passing validation, the curator gets confirmation and can immediately
       begin ingest.
   •   Absence semantics: the schema distinguishes "not recorded," "unknown," and "not
       applicable" from a confirmed value, so missing values are machine-interpretable
       and completeness scores aren't penalized for inapplicable fields.


CUR-2: Correct and enrich metadata. Curators can [EDIT] single or bulk entities in
BioData Registry. This can be done programmatically and through a UI interface. See CUR-
O for validation business rules that should allow/block updates. Changes to an entity are
versioned.

Success criteria:

   •   Scale: curators can edit a single entity or ≥1,000 entities per bulk operation, via both
       UI and API.
   •   Validation: 100% of proposed updates are validated against CUR-0 rules—blocking
       errors prevent submission, optional-field warnings require acknowledgment.
     •   Reliability: ≥99% of valid bulk updates complete successfully, with item-level error
         reporting for failures.
     •   Versioning: 100% of accepted changes create a timestamped version recording
         editor, changed fields, previous values, and update method.

CUR-4: Manage change history & roll backs. A curator browses the timestamped revision
history of a core entity and reverts or supersedes a change, relying on the fact that history is
never destroyed. Instead, entities that were reverted or superseded are archived and
receive a tombstone that points to the new consolidated entity. This avoids dead ends.

Success criteria:

     •   History: curators can browse a complete, timestamped revision history showing
         who changed what.
     •   Revert/supersede: curators can revert to a prior revision or supersede an entity with
         a consolidated version.
     •   Immutability: revision history is immutable—reverting or superseding never deletes
         previous entities or changes.
     •   Archiving: reverted or superseded entities are archived and given a tombstone
         linking to the current consolidated entity.
     •   Redirection: users following an archived entity are automatically directed to its
         replacement, avoiding dead ends while preserving provenance.
     •   Traceability: 100% of rollbacks are logged and traceable, with no changes to
         unrelated data.

ADM — Organization & Space Administrator
Governs who can see and do what, organizes and shares data across Spaces and Organizations,
gates sensitive publishing, and monitors the health of the holdings.

P0
ADM-0: Manage organizing units, users, and roles. An Accelerator admin creates
[organizing units], assigns [organizing unit] admins and members, and sets baseline
permissions within the Accelerator → [organizing unit] hierarchy.

Success criteria:

     •   Unit management: an Accelerator admin can create, edit, deactivate, and view
         organizing units.
     •   User management: admins can add/remove users and assign them as organizing-
         unit admins or members.
     •   Permissions: baseline permissions can be configured at both Accelerator and
         organizing-unit levels; users can access only the units and actions their roles
         permit.
     •   Responsiveness: role and membership changes take effect promptly and are clearly
         reflected in the UI, and the system prevents invalid assignments.
     •   Self-service: 90% of core admin workflows complete without technical support,
         90% of admins report high confidence in core tasks, and 75% can identify and
         correct common configuration errors unaided.
   •   Permission trust: >90% of admins reporting other roles access datasets accurately
       within permissions and hit no unexpected access restrictions.
   •   Non-human principals: agents, pipelines, and service accounts can be issued
       scoped, expiring credentials that act on behalf of a named user, never exceed that
       user's effective permissions, and are attributable to both principal and user in audit
       records.



ADM-1: Data sharing. An Accelerator admin shares specific entities with another
[organizing units] or Accelerator for collaboration.

Entities that can be shared are any explicitly registered entities in BioData Regsitry, e.g. 1)
Donors/subject 2) Specimen 3) Datasets 4) Digital assets 5) Files

Success criteria:

   •   Sharing: an Accelerator admin can share specific registered entities with another
       organizing unit or Accelerator.
   •   Authorization: only authorized admins can initiate, modify, or revoke sharing.
   •   Scope: recipients can access only the entities and actions in the sharing agreement.
   •   Non-destructive: sharing changes and revocations take effect promptly without
       altering or deleting source entities.
   •   Compliance: sensitive or restricted entities remain subject to applicable consent,

   •   Visibility: the interface clearly shows which entities are shared, with whom, at what

   •   Access trust: >90% of admins report other organizing units access datasets

Success criteria:

   •   Exclusion: sensitive content is excluded from search results for users without

   •   Discovery: users with a valid share can discover sensitive data.

AGT —AI Agent
This section covers agentic and AI interaction with the Registry. Capabilities are defined
independently of the surface that delivers them. The Registry exposes its features as a versioned
API, the MCP server wraps that API, and an in-product chat interface, an external MCP client, a
workflow step, and a scientist's own code are all clients of the same operations. A capability is
specified once and reached through any of them.

The Registry, not the agent, remains authoritative. Every caller acts with scoped, auditable
credentials, and Registry services enforce every access decision for the calling principal. An
agent may prepare a proposed change, but an authorized human reviews and approves the
exact version written to the Registry. Natural language is a convenience over the API rather
than a separate path into the data, and it grants no access the caller does not already hold.

Dependencies: this section adds no storage, schema, or permission machinery of its own. It
consumes SCI-1 (query parity across the web application and the API), SCI-2 (natural-language
discovery), SCI-4 (per-entity fitness signals), SCI-5 (locations and manifests), SCI-6 (typed,
traversable relationships), SCI-10 (machine-readable schema, vocabularies, and operations),
SCI-11 (pinned sub-entity selections), CUR-0 (validation, and the distinction between unknown
and not applicable), CUR-1 (registration), CUR-2 (single and bulk edit), CUR-3 (actor- and
version-aware provenance), CUR-4 (versioning and rollback), CUR-7 (review queue for proposed
changes), CUR-9 (readable glossary), ADM-0 (delegated, permission-bounded machine
principals), ADM-2 (sensitivity), ADM-3 (queryable quality signals), and ADM-4 (cost
attribution). Where those use cases already deliver a capability, it is not restated here.

P0

curator, agent, or partner system connects to the Registry through one gateway and can
ask what it is able to do before attempting anything. This gateway is the entry point for

and approved external endpoints reached through it (AGT-6), so a caller finds both in one
place. Every response is filtered to what the calling principal is permitted to use, and the

     •   Vocabulary resolution: free-text terms resolve to controlled vocabulary via the
         glossary, and unresolved terms are reported as unresolved. [CUR-9]
     •   Grounded output: prose is generated only from records the executed call returned,
         with each material claim traceable to a field and version.
     •   Delegated authority: the service executes only operations the calling principal is
         authorized to invoke and holds no standing permissions of its own. [ADM-0]
     •   Measured accuracy: translation accuracy is measured against a fixed set of
         representative requests with known-correct structured calls, reported per release,
         and each translation is logged with the request, compiled call, and surface version.


AGT-4: Assemble a reproducible dataset for a computational experiment. A scientist or
an agent runs a query and receives a pinned selection containing the matching metadata
and resolved paths to the underlying files, which can be exported together to a staging area
for processing. Inclusion and exclusion criteria are recorded with the selection, and the
manifest carries entity identifiers, file locations, metadata versions, and the query that
produced the set. A pinned selection resolves later to identical content or reports what
changed. The Registry reports coverage against the stated criteria and flags structural risks
detectable from metadata: a donor or specimen present on both sides of a proposed split,
a covariate constant within a batch, labels absent or unevenly available, inconsistent
processing versions. Risks that cannot be assessed from metadata are reported as
unassessed. The scientist determines scientific suitability.

Success criteria:

   •   Export: a selection exports as a manifest carrying entity identifiers, resolved file
       locations, metadata versions, and the originating query, to a staging area for
       processing. [SCI-5]
   •   Pinning: pinned selections re-resolve to identical files and metadata versions, or
       report precisely what changed. [SCI-11]
   •   Coverage: coverage is reported against the stated criteria, including how many
       candidates were excluded and why.
   •   Risk reporting: structural risks detectable from metadata are reported; risks not
       assessable from metadata are named as unassessed.
   •   Permission integrity: nothing in the manifest exceeds the caller's permissions; items
       withheld for permission or sensitivity are reported as withheld, not silently omitted.
       [ADM-2]
   •   Reproducibility: a second scientist given only the manifest and the query
       reconstructs the same set.


AGT-5: Machine-assisted ingestion, curation, and harmonization. A data curator,
scientist, or agent brings new data into the Registry or corrects data already in it, and the
Registry performs the schema and vocabulary mapping that would otherwise be done by
hand.

At ingestion, the caller submits files, metadata, protocols, publications, or other
supporting material. The Registry identifies the applicable schema, extracts candidate field
values from what was submitted, and maps free text to controlled vocabulary, so that new
records arrive harmonized rather than requiring a later cleanup pass.

For records already registered, the caller names a scope and the Registry reports values
within it that are inconsistent or unmapped. Examples include one instrument recorded
under several different names across acquisitions, or a cell type that was never mapped to
a controlled term. Corrections are offered as a single reviewable batch rather than one
record at a time.

Both paths produce a proposal rather than a write. Each proposed field records where the
value came from, whether it was extracted from the source or inferred, and a confidence
indicator. Validation runs before a reviewer sees the proposal, and any failure names the
rule that failed. Information the Registry could not determine is recorded as missing or
unknown rather than filled in. An authorised human accepts, edits, or rejects each field in
the standard review queue and approves the exact version written.

This use case follows AGT-4 deliberately. Extraction quality, vocabulary mapping, and
confidence thresholds need iteration to get right, and the least expensive place to iterate is
as computational experiments over datasets assembled through AGT-4, where no result is
written to the Registry.

Initial scope: one agreed schema and one agreed source type for ingestion, and one agreed
harmonization target, end to end. Broader schema coverage, bulk curation, and scheduled
quality sweeps follow once these contracts hold.

Success criteria:

   •   Provenance in proposals: ingestion proposals identify the applicable schema and
       record, per field, the source, whether the value was extracted or inferred, and a
       confidence indicator.
   •   Harmonization: harmonization proposals report inconsistent or unmapped values
       across a caller-specified scope and present corrections as one reviewable batch.
       [CUR-2]
   •   Vocabulary mapping: mappings cite the glossary term identifier resolved to;
       unmapped free text is reported as unmapped. [CUR-9]
   •   Validation: proposals are validated before review, failures name the rule that failed,
       and undetermined information is recorded as missing or unknown rather than
       invented. [CUR-0]
   •   Human review: every proposal enters the standard review queue for per-field
       accept/edit/reject, with explicit human approval of the exact version written. [CUR-
       7]
   •   Attribution: the stored record identifies the proposing principal, the tool and model
       versions, and the approving human. [CUR-3, CUR-4, ADM-0]
P2
AGT-6: Orchestrate multi-step plans. A caller requests work requiring more than one
operation, for example retrieving a cohort, running a quality check across it, comparing two
groups, and registering the result. The Registry returns a plan naming the operations and
tools each step will use, and the caller approves or edits it before execution begins. Each
step records its inputs, outputs, tool and model version, acting principal, and the user on
whose behalf it ran. A failed step halts the plan without leaving partial Registry state.
Artifacts a plan produces can be registered back, marked as machine-produced and linked
to their inputs and to the plan that produced them. Re-running a recorded plan against
pinned inputs reproduces the result or reports why it diverged.

Success criteria:

     •   The plan is returned for approval or editing before execution begins, naming the
         operations and tools each step will use.
     •   Each step records inputs, outputs, tool and model version, acting principal, and the
         user on whose behalf it ran. [ADM-0, CUR-3]
     •   A failed step halts the plan, identifies which steps completed, and leaves no partial
         Registry state.
     •   Artifacts registered back are marked machine-produced and linked to their inputs
         and to the plan that produced them. [CUR-1, CUR-3]
     •   Re-running a recorded plan against pinned inputs reproduces the result or reports
         why it diverged. [SCI-11]
     •   Any step that mutates the Registry requires human approval through the AGT-5 path,
         and resource use per plan is attributable. [ADM-4]

PRT-8: Ask for data. Whether for cost savings (to avoid hot storage) or for legal reasons a

PRT-3: Consume metadata programmatically. A partner's pipeline or agent queries the

authentication, then reaches the referenced data through its listed location.

DOI resolves to the Registry landing page with its manifest, contributors, license, and asset
references.
